# コンポーネントとフレームワークの進化

コンポーネントとフレームワークの歴史は、「同じ機能を毎回ゼロから作らず、実績のある部品と枠組みを再利用する」方向への進化として捉えられます。

まず言葉の違い

- ライブラリ
  - よく使う関数やクラスをまとめたもの。
  - 必要なときに、開発者のコードから呼び出す。
  - 例：文字列処理、画像変換、暗号化、通信ライブラリ。
- コンポーネント
  - 明確な役割と接続方法を持つ、交換・再利用可能なソフトウェア部品。
  - 内部の実装を知らなくても、公開されたインターフェースを通じて利用できる。
  - 例：ボタン、地図表示、データベース接続、通信ドライバ。
- フレームワーク
  - アプリケーション全体の基本構造と実行の流れを提供する枠組み。
  - 開発者は、決められた位置に固有の処理を追加する。
  - 例：Qt、Spring、Django、Ruby on Rails。

最も大きな違いは、処理を呼び出す方向です。

- ライブラリ：自分のコードがライブラリを呼ぶ
- フレームワーク：フレームワークが自分のコードを呼ぶ
- コンポーネント：決められた接続方法でほかの部品と組み合わせる

フレームワークが開発者のコードを呼び出す仕組みは、制御の反転と呼ばれます。

## 進化の歴史

### 1950〜60年代：サブルーチンとライブラリ

- 初期のプログラムでは、同じ計算や入出力処理を何度も記述していた。
- そこで、共通処理をサブルーチンや関数として切り出すようになった。
- 数学計算、ファイル操作、文字処理などがライブラリとして配布された。
- 再利用の単位は、比較的小さな関数だった。
- プログラム全体の構造は、それぞれの開発者が設計していた。

この段階では、再利用できる「道具」はあっても、アプリケーションの「組み立て方」までは共通化されていませんでした。

### 1960〜70年代：OSとランタイムという共通基盤

- OSが、ファイル、メモリ、画面、通信などの共通機能を提供するようになった。
- コンパイラと標準ライブラリによって、ハードウェアの細部を直接扱う必要が減った。
- アプリケーションはOSが提供する決められた方法で動作するようになった。
- これは現在のフレームワークにつながる「共通の実行基盤」という発想だった。

例えば、アプリケーションが好きなタイミングで画面入力を調べるだけでなく、OSが入力イベントをアプリケーションへ通知する仕組みが生まれました。

### 1960〜70年代：オブジェクト指向の誕生

- SimulaやSmalltalkによって、データと処理をオブジェクトとしてまとめる考え方が発展した。
- Smalltalkでは、画面部品や開発環境そのものが、再利用可能なオブジェクトとして構成された。
- 継承によって既存部品を拡張する考え方も広まった。
- これにより、単なる関数より大きな単位を部品として扱いやすくなった。

ただし、クラスとコンポーネントは同じではありません。

- クラスは、主にプログラミング言語内部の設計単位。
- コンポーネントは、外部との接続方法や交換可能性を持つ、より独立した単位。

一つのコンポーネントが、複数のクラスで作られることもあります。

### 1970〜80年代：GUIフレームワーク

- GUIでは、ボタン、ウィンドウ、メニューなど共通する部品が多い。
- マウスやキーボードからの入力を待ち、発生したイベントに応じて処理する必要がある。
- この共通の実行構造をGUIフレームワークが担当するようになった。

典型的な流れは次のとおりです。

1. フレームワークがアプリケーションを起動する
2. フレームワークが入力イベントを待つ
3. ボタンが押されたら、登録された処理を呼び出す
4. 画面を再描画する
5. 再びイベントを待つ

開発者はイベントループ全体を作らず、「このボタンが押されたら何をするか」を記述すればよくなりました。

この仕組みは、現在のQtなどにも引き継がれています。

### 1980年代：アプリケーションフレームワーク

- GUIだけでなく、アプリケーション全体の共通構造を提供するフレームワークが登場した。
- 画面生成、イベント処理、ファイル保存、印刷、エラー処理などが共通化された。
- 開発者は、フレームワークが用意した基底クラスを継承し、必要な部分を上書きした。
- 「共通処理はフレームワーク、製品固有処理は開発者」という役割分担が形成された。

この時代は、継承による拡張がフレームワーク設計の中心でした。

利点：

- 短期間で統一されたアプリケーションを作れる
- OS固有の処理をフレームワークへ任せられる
- 複数のアプリケーションで設計を統一できる

問題：

- フレームワークの内部構造を理解する必要がある
- 基底クラスへの依存が強くなる
- 継承関係が深くなり、変更の影響が分かりにくくなる

### 1980〜90年代：コンポーネント指向

- オブジェクトを、言語やプログラムの境界を越えて利用したいという要求が高まった。
- 内部実装ではなく、公開されたインターフェースを通じて部品を利用する考え方が発展した。
- コンポーネントには、次のような性質が求められた。
  - 明確な役割を持つ
  - 接続方法が定義されている
  - 内部実装を隠している
  - 単独で交換・更新できる
  - 別の製品でも再利用できる
  - バージョンを管理できる

例えばデータベース接続コンポーネントを交換しても、利用側のコードは同じインターフェースを使い続けられる、という考え方です。

### 1990年代：バイナリコンポーネント

- ソースコードを共有しなくても、コンパイル済みの部品を利用できる仕組みが普及した。
- 代表例として、MicrosoftのCOM、ActiveX、OLEなどがある。
- Windowsアプリケーション間で、文書、画面部品、通信機能などを連携できた。
- Visual Basicなどでは、コンポーネントを画面へ配置し、プロパティを設定するだけで利用できた。

これにより、部品を「プログラムとして記述するもの」だけでなく、開発ツール上で組み立てるものとして扱えるようになりました。

一方で、次の問題も起きました。

- コンポーネントのバージョン衝突
- 必要な部品がPCにインストールされていない
- 古い部品の更新によって別のアプリが動かなくなる
- OSや実行環境への強い依存

Windowsでは、こうした問題が俗に「DLL地獄」と呼ばれました。

### 1990年代：分散コンポーネント

- ネットワーク上の別のコンピューターにある部品を、手元の部品のように呼び出す仕組みが登場した。
- CORBA、DCOM、Java RMIなどが代表例。
- 異なる言語やOSの間でも、決められたインターフェースを通じて連携することを目指した。
- 大規模な業務システムで利用された。

しかし、ネットワーク越しの処理には次の問題があります。

- 通信が遅い
- 接続が途中で切れる
- 相手が停止していることがある
- 一部だけ処理が成功することがある
- バージョンが一致しないことがある

「遠隔の部品をローカルの部品と同じように扱える」という考え方には限界があることも分かってきました。

### 1990〜2000年代：企業向けフレームワーク

- 企業システムでは、認証、データベース、トランザクション、ログ、通信などの共通処理が必要になった。
- Java EE、.NETなどが、これらの実行基盤を提供した。
- 開発者は業務処理をコンポーネントとして実装し、共通処理を基盤に任せた。
- 大規模システムを統一的に構築できる一方、設定や仕組みが複雑になった。

フレームワークを使うためだけに大量の定型コードや設定を書く問題も生まれました。

### 1990年代後半：デザインパターン

- フレームワークやコンポーネントで繰り返し使われる設計方法が、デザインパターンとして整理された。
- 代表例は次のとおり。
  - Observer
     状態変化を複数の相手へ通知する。
  - Factory
    - 具体的な生成方法を利用側から隠す。
  - Adapter
    - 異なるインターフェースを接続する。
  - Strategy
    - 処理方法を交換可能にする。
  - Model-View-Controller
    - データ、画面、操作を分離する。

デザインパターンは完成した部品ではなく、部品を組み合わせる設計上の型です。

### 2000年代：Webアプリケーションフレームワーク

- Webシステムが普及し、HTTP通信、URL処理、認証、画面生成、データベース接続などを共通化するフレームワークが発展した。
- Struts、Spring、Django、Ruby on Railsなどが登場した。
- Webアプリケーションの典型的な構造が標準化された。

例えば、URLへのアクセスに対して、

1. リクエストを受け取る
2. 対応する処理を選ぶ
3. データベースを操作する
4. HTMLまたはJSONを生成する
5. レスポンスを返す

という流れをフレームワークが担当します。

特にRuby on Railsは、設定より規約という考え方を広めました。

- 標準的な名前や配置に従えば、細かな設定を書かなくても動く。
- 開発速度は上がるが、規約から外れた処理では扱いにくくなる。

### 2000年代：依存性注入と疎結合化

- 継承中心のフレームワークは、特定の基底クラスへの依存が強くなる問題を抱えていた。
- そこで、必要な部品を外部から渡す**依存性注入（DI）**が普及した。

例えば制御ロジックが通信処理を直接生成せず、外部から受け取るようにします。

- 製品ではCAN通信部品を渡す
- テストでは模擬通信部品を渡す
- 別製品ではEthernet通信部品を渡す

これにより、利用側と具体的な実装を分離しやすくなりました。

設計の中心も、次のように変化しました。

- 継承して機能を追加する
- 部品を組み合わせて機能を構成する

現在は一般に、深い継承より**コンポジション（合成）**が好まれる傾向があります。

### 2000〜2010年代：パッケージ管理の発展

- コンポーネントの配布とバージョン管理を自動化する仕組みが普及した。
- Maven、NuGet、npm、pip、Cargoなどが代表例。
- 必要なライブラリやコンポーネントを、定義ファイルから自動取得できるようになった。
- ある部品が必要とする別の部品も、自動的に解決されるようになった。

これにより再利用は非常に容易になりましたが、新しい問題も生まれました。

- 依存するパッケージが増えすぎる
- バージョンが衝突する
- 更新によって互換性が失われる
- 利用している部品に脆弱性が見つかる
- 小さな外部部品の停止や削除が広範囲に影響する

現在では、部品を作る能力だけでなく、依存関係を管理する能力が重要になっています。

### 2010年代：フロントエンドコンポーネント

- Web画面が高度化し、画面を再利用可能なコンポーネントに分割する考え方が広まった。
- React、Vue、Angularなどが代表的。
- ボタンのような小さな部品から、検索画面や地図画面のような大きな部品まで構成できる。
- コンポーネントごとに、表示、状態、イベント処理をまとめる。

例えば顧客一覧画面を、次のように分けます。

- 検索条件コンポーネント
- 顧客テーブルコンポーネント
- ページ切り替えコンポーネント
- 顧客詳細コンポーネント

これにより、画面全体を一枚の巨大なプログラムとして作らずに済みます。

Qt/QMLのButton、ListView、独自QMLコンポーネントにも近い考え方です。

### 2010年代：サービスとコンテナ

- コンポーネントの境界が、一つのプログラム内部から、独立して動作するサービスへ広がった。
- REST APIやメッセージキューを通じてサービスを接続するようになった。
- Dockerなどのコンテナによって、プログラムと実行環境を一体として配布できるようになった。
- Kubernetesなどが、多数のコンテナの配置、監視、再起動を管理するようになった。

コンポーネントの単位は、歴史的に次のように拡大しました。

1. 関数
2. クラス
3. ライブラリ
4. アプリケーション内部のコンポーネント
5. バイナリ部品
6. ネットワーク上のサービス
7. 実行環境を含むコンテナ

ただし、大きければ優れているわけではありません。サービスとして分離すると、通信障害やデータ整合性など、新しい複雑さが発生します。

### 2010年代以降：クラウドフレームワークとマネージドサービス

- データベース、認証、監視、メッセージングなどを、クラウド事業者が完成したサービスとして提供するようになった。
- 開発者はソフトウェア部品だけでなく、クラウドサービスを組み合わせてシステムを作る。
- サーバーレスでは、フレームワークやクラウド基盤が実行タイミングやサーバー管理を担当する。
- 開発者は、HTTP要求やキュー受信時に実行される処理を記述する。

再利用の対象が、コードから運用を含む機能全体へ広がったといえます。

### 組み込み開発における進化

組み込み分野でも、次のような形でコンポーネント化が進みました。

- CPUベンダーのHAL
- デバイスドライバ
- RTOS
- 通信スタック
- ファイルシステム
- GUIフレームワーク
- ミドルウェア
- AUTOSARのソフトウェアコンポーネント
- ROS 2のノードとコンポーネント

例えばCAN通信を、次の階層へ分けられます。

- CANコントローラドライバ
- CANフレーム送受信
- J1939プロトコル
- 車両・機械固有のメッセージ処理
- 制御ロジック
- 画面表示

この構造なら、通信ドライバを変更しても、J1939より上の処理への影響を抑えられます。

一方、組み込みでは次の制約があります。

- メモリ容量
- CPU性能
- 起動時間
- リアルタイム性
- 安全性
- 長期保守
- ハードウェア依存
- 認証や規格への適合

そのため、Web開発のように大量の外部コンポーネントを簡単に追加できるとは限りません。

## コンポーネントとフレームワークの関係

両者は対立するものではありません。

- フレームワークが、アプリケーション全体の構造と実行方法を決める。
- コンポーネントが、その構造の中で個別の機能を担当する。
- ライブラリが、コンポーネントの内部で必要な処理を提供する。

Qtを例にすると、

- Qt：アプリケーションフレームワーク
- Qt Quick／QML：画面構築のフレームワーク
- ButtonやListView：既成のコンポーネント
- 独自のCameraContainer：製品固有のコンポーネント
- 画像処理・JSONライブラリ：内部で利用する道具
- アプリケーションコード：それらを組み合わせた製品

という関係になります。

## 発展によって得られたものと問題点

## 得られたもの

- 同じ機能を何度も作らずに済む
- 実績のある部品を利用できる
- 開発者ごとの作り方を統一できる
- OSやハードウェアの違いを隠せる
- 分業しやすくなる
- 部品単位でテストしやすくなる
- 一部を交換・改善しやすくなる
- 製品間で機能を再利用できる

## 同時に生まれた問題

- フレームワークの学習が必要になる
- フレームワーク独自の作法に縛られる
- 内部動作が見えにくくなる
- バージョンアップの影響が大きい
- 外部コンポーネントの品質に依存する
- 依存関係が増え、全体を把握しにくくなる
- 簡単な処理でもフレームワークに合わせる必要がある
- フレームワーク自体の開発終了が製品寿命に影響する

## 全体の流れ

コンポーネントの進化は、次のようにまとめられます。

1. 共通処理を関数にする
2. 関数をライブラリとして配布する
3. データと処理をクラスにまとめる
4. 公開インターフェースを持つ独立部品にする
5. 言語やプログラムを越えて部品を利用する
6. ネットワーク越しのサービスとして利用する
7. 実行環境を含むコンテナとして配布する
8. 運用を含むクラウドサービスとして利用する

フレームワークの進化は、次のように整理できます。

1. OSが基本的な実行環境を提供する
2. GUIのイベント処理を共通化する
3. アプリケーション全体の基本構造を提供する
4. Webや企業システムの典型的な構造を標準化する
5. 継承中心から、部品の組み合わせ中心へ移る
6. 開発だけでなく、テスト、配布、運用まで管理する

最終的な目的は、単に部品を増やすことではありません。変化しやすい部分と変化しにくい部分の間に、安定した境界を作ることです。

良いコンポーネントは内部を自由に変更でき、良いフレームワークはアプリケーションごとの違いを受け入れながら、共通する仕組みを引き受けます。
