# ソフトウェア構造の進化の歴史

ソフトウェア構造の進化は、ひと言でいえば、大きく複雑になるプログラムを、人間が理解・変更できる大きさに分ける工夫の歴史です。

## オブジェクト指向登場前

ソフトウェアの誕生から、産業として成立するまでの歴史

- 1940〜50年代：機械語
  - CPUが直接実行できる数値を並べてプログラムを作成。
  - 処理の流れもメモリの位置も、すべて人間が管理した。
  - 小さなプログラムでも理解や修正が非常に難しかった。
- 1950年代：アセンブリ言語
  - 数値の命令を、ADDやJMPなどの名前で書けるようになった。
  - ラベルを使って処理位置を表せるようになった。
  - ただし、CPUごとの命令やレジスタを強く意識する必要があった。
- 1950〜60年代：高級言語と手続き化
  - FORTRAN、COBOL、ALGOLなどが登場。
  - 「計算する」「表示する」といった処理を、人間に近い表現で書けるようになった。
  - よく使う処理を関数・サブルーチンとして切り出し、再利用できるようになった。
- 1960〜70年代：構造化プログラミング
  - 無秩序なジャンプ命令であるgotoを減らし、処理を次の基本構造で組み立てる考え方。
    - 順番に実行する
    - 条件で分岐する
    - 繰り返す
  - 「上から順に読めるプログラム」を目指した。
  - C、Pascalなどが代表的。
  - 現在のPLCラダーでも、処理を状態や機能単位に整理する際の基礎になる。
- 1970年代：トップダウン設計と階層化
  - 大きな目的を、より小さな処理へ段階的に分解する考え方。
  - 例えば「機械を自動運転する」を、次のように分ける。
    - 入力を取得する
    - 状態を判断する
    - 出力を制御する
    - 異常を監視する
  - さらに各処理を細分化し、木のような階層に整理する。
  - 全体を一度に考えず、理解できる単位へ分けることが目的。
- 1970〜80年代：モジュール化
  - 関連するデータと処理を、独立した部品であるモジュールにまとめる。
  - 外部には必要な入口だけを公開し、内部の実装を隠す。
  - 例えば通信モジュールを使う側は、内部のUART制御を知らなくてもsend()を呼べばよい。
  - 修正の影響をモジュール内部に閉じ込めやすくなった。
- 1970〜80年代：データ抽象化と情報隠蔽
  - データを直接操作せず、決められた操作を通じて扱う考え方。
  - 例えばモーターの速度値を変数へ直接代入せず、setSpeed()を通して設定する。
  - 範囲チェックや安全処理を一か所にまとめられる。
  - 後のオブジェクト指向につながった。

## オブジェクト指向登場後

ソフトウェア開発が高度化・大規模化した末の、大量生産の時代の歴史

- 1980〜90年代：オブジェクト指向
  - データと、それを扱う処理をオブジェクトとして一体化する。
  - 主な考え方は次のとおり。
    - カプセル化：内部状態を隠す
    - 継承：既存の型をもとに新しい型を作る
    - ポリモーフィズム：種類が違っても共通の方法で操作する
  - 例えばMotor、Valve、Sensorを、それぞれ現実の装置に対応した部品として表現できる。
  - Smalltalk、C++、Javaなどで広く普及した。
- ただし、オブジェクト指向は「構造化の次に完全に置き換わったもの」ではない
  - オブジェクトの中では、現在も条件分岐や繰り返しなどの構造化プログラミングを使う。
  - モジュール化、階層化、オブジェクト指向は、異なる観点から同時に利用される。
  - 「新しい方式が古い方式を廃止した」というより、整理の道具が増えたと考えると分かりやすい。
- 1980〜90年代：階層型・レイヤードアーキテクチャ
  - プログラム全体を役割ごとの層に分ける考え方。
  - 一般的な例は次のようになる。
    - 画面・操作層
    - 業務・制御ロジック層
    - データアクセス層
    - ハードウェア・データベース層
  - 上位の処理が、下位の細かな実装を直接扱わないようにする。
  - 画面やデータベースを交換しやすくなる。
- 1990〜2000年代：コンポーネントとフレームワーク
  - ソフトウェアを、交換・再利用可能な大きな部品として組み合わせる方向へ発展。
  - GUI、通信、データベース接続などの共通処理を、ライブラリやフレームワークとして利用する。
  - Qt、.NET、Java EEなどが代表例。
  - 開発者はすべてを自作せず、既存の枠組みに必要な処理を追加するようになった。
- 2000年代：設計パターンと依存関係の整理
  - 多くの開発で繰り返し現れる設計上の問題に、共通の解決方法が整理された。
  - 例えば次のようなものがある。
    - Factory：オブジェクトの生成方法をまとめる
    - Observer：状態の変化を複数の相手へ通知する
    - Strategy：処理方法を交換可能にする
  - 一方で、パターンを使いすぎると、かえって構造が複雑になる問題も生まれた。
  
## サービス化の歴史

ソフトウェアを単体ではなく、複合的なものとして責任の分散化をすすめた歴史
  
- 2000年代：サービス指向と分散化
  - 一つの巨大なプログラムだけでなく、複数のシステムをネットワーク経由で連携させるようになった。
  - 例えば認証、顧客管理、在庫管理を別サービスとして分離する。
  - コード内部の構造だけでなく、システム同士をどう分割するかが重要になった。
- 2010年代：マイクロサービス
  - 大きなシステムを、独立して開発・配布できる小さなサービスに分割する。
  - サービスごとに担当チームやデータベースを持つこともある。
  - 部分的な変更や拡張はしやすいが、通信障害、データ整合性、監視などの問題が増える。
  - 小規模システムでは、分割しない方が単純で保守しやすい場合も多い。
- 2010年代以降：ドメイン駆動設計（DDD）
  - 技術的な都合だけでなく、業務や対象分野の意味に沿って構造を作る。
  - 例えば建設機械なら、単なるdata1やflag2ではなく、Outrigger、RatedLoad、EmergencyStopといった用語で表現する。
  - ソフトウェアの構造と、現場の人が考える業務構造を近づける考え方。
- 2010年代以降：クリーンアーキテクチャなど
  - 重要な制御・業務ロジックを、画面、データベース、通信方式、OSなどから独立させる。
  - 内側に重要なルールを置き、外側に交換されやすい技術を置く。
  - 例えば制御判定をQt画面やAzure通信から分離すれば、画面やクラウドを変更しても判定ロジックを再利用しやすい。

## アーキテクチャの現在位置

- 並行して発展した関数型プログラミング
  - オブジェクトの状態を変化させ続けるのではなく、入力から出力を求める関数を組み合わせる。
  - 状態変化を減らすことで、並列処理やテストを行いやすくする。
  - 現在は「オブジェクト指向か関数型か」の二択ではなく、両方の長所を組み合わせることが多い。
- 現在：目的に応じて複数の方法を併用
  - 関数の内部は構造化する。
  - 関連する処理はモジュールにまとめる。
  - 状態を持つ装置や概念はオブジェクトとして表現する。
  - システム全体は層やサービスに分割する。
  - 重要な制御ロジックは、外部技術への依存を減らす。
  - つまり現在の設計は、過去の考え方を積み重ねたものになっている。

## アーキテクチャの進化の振り返り

1. 命令を直接並べる
2. 処理を関数に分ける
3. 処理の流れを規則的にする
4. 関連する処理をモジュールにまとめる
5. データと処理をオブジェクトにまとめる
6. プログラム全体を層やコンポーネントに分ける
7. システムをサービス単位に分ける
8. 技術ではなく、業務や変更理由を基準に境界を決める

ただし、最終的な目標は細かく分割すること自体ではありません。どこを変更したとき、どこまで影響するのかを予測できる構造にすることが、これらすべてに共通する目的です。
