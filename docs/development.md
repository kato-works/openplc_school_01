# 開発方法論

開発方法論の進化は、ひと言でいえば、「何を、どの順番で作り、どう確認し、どう変更に対応するか」についての工夫の歴史です。

## 開発の進化

### 1950〜60年代：計画中心の開発

- 初期のコンピューターは高価で、実行や修正にも大きなコストがかかった。
- 最初に仕様を決め、設計してから実装するという、建築や製造業に近い進め方が採用された。
- プログラムを完成させた後に、まとめてテストすることも多かった。
- 小規模で要件が明確なら成立するが、大規模化すると後半で問題が集中した。

### 1970年代：ウォーターフォールモデル

- 開発を明確な工程に分け、原則として上流から下流へ順番に進める。
  - 要求分析
  - 要件定義
  - 基本設計
  - 詳細設計
  - 実装
  - テスト
  - 運用・保守
- 水が上から下へ流れるように工程が進むため、ウォーターフォールと呼ばれる。
- 各工程で文書を作り、承認を得て次へ進む。
- 全体計画、予算、納期、契約範囲を明確にしやすい。
- 一方、開発後半で要求の間違いが分かると、大きな手戻りが発生する。
- 「最初に正しい仕様を決められる」という前提が強い。

向いている例：

- 法規や規格によって要求が明確に決まっている
- ハードウェアを含み、後から簡単に変更できない
- 発注側と受注側の責任範囲を契約で明確にしたい
- 同じ種類の製品を繰り返し開発している

### 1970年代以降：V字モデル

- ウォーターフォールを、設計とテストの対応関係が分かるように整理したもの。
- 左側で要求から詳細設計へ進み、右側で単体テストから受け入れテストへ進む。

| 設計工程 | 対応するテスト |
| --- | --- |
| 要求分析 | 受け入れテスト |
| システム設計 | システムテスト |
| 基本設計 | 結合テスト |
| 詳細設計 | 単体テスト |

- 「何を確認するためのテストなのか」が明確になる。
- 組み込み、車載、医療、安全関連などで現在も重要。
- ただし、仕様の変更に弱い点はウォーターフォールと共通する。

### 1970〜80年代：反復型・漸進型開発

- 最初から完成品を一度に作らず、何度か繰り返しながら完成させる。
- 反復型は、同じ機能を繰り返し改善する考え方。
- 漸進型は、使える機能を少しずつ追加する考え方。

例えば機械制御なら、

- 第1段階：手動操作だけ動かす
- 第2段階：センサー入力を追加する
- 第3段階：自動運転を追加する
- 第4段階：異常監視を追加する

という形で進める。

- 早い段階で実物を確認できる。
- 問題を小さいうちに発見しやすい。
- 一方、全体設計を考えずに機能を足し続けると、構造が崩れやすい。

### 1980年代：プロトタイピング

- 本格開発の前に、試作品を作って要求や技術を確認する。
- 画面、操作性、新しいセンサー、通信方式、画像認識など、作ってみないと判断できないものに有効。

主に二つの方法がある。

- 使い捨て型
  - 要求を確認するためだけに作り、本番には流用しない。
- 進化型
  - 試作品を改良しながら、本番システムへ発展させる。

進化型では、実験用コードがそのまま製品に残り、保守しにくくなる危険がある。

### 1980年代：スパイラルモデル

- 開発を何周かのサイクルに分け、各周回で次を行う。
  1. 目標を決める
  2. リスクを分析する
  3. 試作・開発する
  4. 評価して次の計画を立てる
- 最大の特徴は、リスクの高い部分から確認すること。
- 例えば、初めに画面を完成させるのではなく、成立するか分からない通信や制御方式を先に試す。
- 大規模で不確実性の高い開発に向いている。
- リスク分析に経験が必要で、管理方法も複雑になりやすい。

### 1990年代：RAD

- RADはRapid Application Developmentの略。
- 短期間で試作品を作り、利用者の意見を受けながら完成させる。
- GUIツール、部品の再利用、データベースなどを活用する。
- 業務アプリや画面中心のシステムに向いている。
- 素早く作れる一方、速度を優先して設計や品質管理が不足することもある。

### 1990年代：オブジェクト指向開発方法論

- オブジェクト指向が普及し、分析、設計、実装を一貫したモデルで扱おうとした。
- UMLによるクラス図、シーケンス図、状態遷移図などが使われるようになった。
- RUPなど、反復型開発とオブジェクト指向設計を組み合わせた方法も登場した。
- 文書やモデルを作りすぎると、実装より設計作業が重くなる問題もあった。

### 1990年代後半：XP

- XPはExtreme Programmingの略。
- 変化が多い開発で、コードの品質を保ちながら素早く変更する方法を重視する。
- 代表的な実践は次のとおり。
  - 短い開発サイクル
  - 小さなリリース
  - テストの自動化
  - ペアプログラミング
  - 継続的な設計改善
  - コードの共同所有
  - 継続的インテグレーション
  - 顧客との頻繁な対話
- 計画をなくすのではなく、小さく計画して頻繁に修正する考え方。
- 後のアジャイル開発に大きな影響を与えた。

### 1990年代後半：テスト駆動開発（TDD）

- TDDは、実装より先にテストを書く開発方法。
- 基本は次の短いサイクルを繰り返す。
  1. Red
    - まだ機能がないため失敗するテストを書く。
  2. Green
    - テストを通すための最小限のコードを書く。
  3. Refactor
    - 動作を変えずにコードを整理する。

例えば「速度は0〜100の範囲だけ設定できる」という要求なら、

- 50が設定できる
- 100が設定できる
- 101は拒否される
- 負の値は拒否される

というテストを先に作る。

TDDの利点：

- 仕様を具体的な入力と結果として考えられる
- 修正後に既存機能が壊れていないか確認できる
- テストしやすい、小さく分離された設計になりやすい

注意点：

- 画面の見た目やハードウェア動作には適用しにくい部分がある
- テストを通すことと、製品要求を満たすことは同じではない
- 実機試験、結合試験、安全試験は別途必要
- テストの書き方が悪いと、変更しにくいテストが大量に残る

TDDは開発全体の管理方法ではないため、スクラムやウォーターフォールの中でも利用できる。

### 2001年以降：アジャイル開発

- 2001年の「アジャイルソフトウェア開発宣言」を契機に広まった考え方。
- 最初にすべてを固定するのではなく、動くソフトウェアを早く作り、利用者の反応を受けて改善する。
- 主に次を重視する。
  - 人同士の対話
  - 実際に動くソフトウェア
  - 顧客との協力
  - 変化への対応
  - 文書、契約、計画を不要とする考え方ではない。
  - それらも必要だが、実物や対話をより重視するという意味。
- 「アジャイル」は単一の具体的方法ではなく、価値観や考え方の総称。

### 1990年代〜現在：スクラム

- スクラムは、アジャイルな開発を進めるためのチーム運営の枠組み。
- 1〜4週間程度の短い期間であるスプリントを繰り返す。
- 各スプリントで、利用可能な成果を作ることを目指す。

主な役割：

- プロダクトオーナー
  - 何を優先して作るかを決める。
- スクラムマスター
  - チームがスクラムを適切に進められるよう支援する。
- 開発者
  - 設計、実装、テストなどを行い、成果を完成させる。

主な管理対象：

- プロダクトバックログ
  - 今後必要な機能や改善の一覧。
- スプリントバックログ
  - 今回のスプリントで行う作業。
- インクリメント
  - スプリントによって完成した、利用可能な成果。

主なイベント：

- スプリントプランニング
- デイリースクラム
- スプリントレビュー
- レトロスペクティブ（振り返り）

スクラムの利点：

- 短い間隔で方向を修正できる
- 優先順位の高い機能から作れる
- 問題や進捗をチームで共有しやすい

注意点：

- 毎日会議をするだけではスクラムにならない
- スプリント内に作業を詰め込むだけでは、単なる短期ウォーターフォールになる
- プロダクトオーナーが優先順位を決められないと機能しにくい
- ハードウェア待ちや外部承認が多い開発では工夫が必要

### イシュードリブン開発

- 実装、障害、改善、調査などの作業を、**Issue（課題）**として登録して進める方法。
- GitHub Issues、GitLab Issues、Jiraなどがよく使われる。
- 一般的には次の流れになる。
  - 問題や要求をIssueとして登録する
  - 完了条件を記載する
  - 担当者と優先順位を決める
  - Issueに対応するブランチを作る
  - 実装とテストを行う
  - レビュー後にマージする
  - Issueを完了にする

良いIssueには、次のような情報を含める。

- 背景と目的
- 現在の問題
- 期待する結果
- 完了条件
- 対象外の範囲
- 関連資料やログ

利点：

- 「なぜこの変更を行ったか」が記録に残る
- 作業の抜けや重複を防ぎやすい
- コード変更と要求を関連付けられる
- 遠隔チームでも状況を共有しやすい

注意点：

- Issueを細かく分けすぎると、登録や更新が目的になってしまう
- 「ボタンを作る」のような作業だけでなく、目的や完了条件を書く必要がある
- Issue管理は、製品全体の優先順位や設計判断を自動的に行ってくれるわけではない

イシュードリブンは、スクラムと組み合わせられる。

- プロダクトバックログをIssueで管理する
- スプリント対象のIssueを選ぶ
- Issueごとに実装、テスト、レビューする

という使い方ができる。

### 2000年代：カンバン方式

- 作業をカードとして見える化し、状態ごとに並べる方法。
- 典型的な列は次のようになる。
  - 未着手
  - 対応中
  - レビュー中
  - テスト中
  - 完了
- 最大の特徴は、同時に進める作業数を制限すること。
- 新しい仕事を次々に始めず、進行中の仕事を先に完了させる。
- 運用保守、問い合わせ対応、障害対応など、作業が随時発生する仕事に向いている。
- スクラムのような固定スプリントを必須としない。

### 2000年代以降：リーン開発

- 製造業のリーン生産方式をソフトウェア開発へ応用した考え方。
- 利用者に価値を与えない作業を減らし、必要なものを早く届ける。
- 代表的な方針は次のとおり。
  - 不要な機能を作らない
  - 待ち時間を減らす
  - 作りかけの仕事を減らす
  - 品質を後から確認するのではなく、工程内で作り込む
  - 判断を必要な時点まで遅らせる
  - チーム全体を最適化する
- 「開発速度を上げる」というより、手戻りや待ち時間を減らす考え方。

### 2000〜2010年代：継続的インテグレーション

- 複数の開発者による変更を、長期間分離せず、頻繁に統合する。
- コードを共有リポジトリへ反映するたびに、自動で次を実行する。
  - ビルド
  - 静的解析
  - 単体テスト
  - 結合テスト
  - コーディング規約の確認
- 問題を早い段階で発見できる。
- Gitのブランチを長期間分岐させると統合が難しくなるため、小さな変更を頻繁に統合する。

### 2010年代：DevOpsとCI/CD

- 開発担当と運用担当を完全に分離せず、開発から運用までを継続的に改善する考え方。
- CI/CDによって、ビルド、テスト、配布を自動化する。
  - CI
    - 変更を頻繁に統合し、自動的に検証する。
  - 継続的デリバリー
    - いつでもリリースできる状態まで自動化する。
  - 継続的デプロイ
    - テストに合格した変更を、本番環境まで自動的に反映する。
- Webサービスでは本番まで自動化しやすい。
- 組み込み製品では、実機書き込み、HIL試験、承認、出荷判定などがあるため、途中に人間の承認を設けることが多い。

### 2010年代以降：ユーザーストーリーとBDD

- 機能を技術者の作業ではなく、利用者の目的から表現する。

典型的なユーザーストーリー：

- オペレーターとして、異常発生時に対象装置を確認したい。なぜなら、停止すべきか判断したいからだ。

- BDDはBehavior-Driven Developmentの略。
- システムの振る舞いを、具体的な状況、操作、結果で記述する。

例えば、

- 前提：機械が自動運転中である
- 条件：非常停止入力がOFFになった
- 結果：すべての駆動出力が停止する

という形で表す。

- 要求、テスト、実装の認識を合わせやすい。
- TDDがコード設計に近いのに対し、BDDは利用者から見た振る舞いに重点を置く。

### 現在：ハイブリッド型開発

実際の製品開発では、一つの方法だけを純粋に採用することは少なくなっています。

例えば組み込み製品なら、次のように組み合わせられます。

- 製品全体の要求と安全設計はV字モデルで管理する
- 不確実な通信やセンサー部分はプロトタイプで確認する
- 機能開発は2週間単位のスクラムで進める
- 作業はIssueとして記録する
- 制御ロジックはTDDで実装する
- 実機試験はテスト仕様書に従って実施する
- ビルドと単体テストはCIで自動化する
- リリース前には人間が承認する

つまり、次のように役割が違います。

| 方法 | 主に決めること |
| --- | --- |
| ウォーターフォール | 工程をどの順番で進めるか |
| V字モデル | 設計とテストをどう対応させるか |
| スパイラル | 技術的リスクをどう減らすか |
| アジャイル | 変化へどう対応するか |
| スクラム | チームが短期間の仕事をどう進めるか |
| カンバン | 作業の流れと同時進行数をどう管理するか |
| イシュードリブン | 個々の要求や作業をどう記録するか |
| TDD | コードと単体テストをどう作るか |
| BDD | 要求を具体的な振る舞いとしてどう表すか |
| DevOps・CI/CD | 開発から配布・運用までをどう自動化するか |

開発方法論の進化を大まかにまとめると、次の流れになります。

1. 最初にすべて計画してから作る
2. 設計とテストの対応を明確にする
3. 試作品や反復によって不確実性を減らす
4. 小さな単位で完成品を作り、評価を受ける
5. 要求や作業をIssueとして追跡する
6. テストを開発の後ではなく、開発中に作り込む
7. ビルド、テスト、配布を自動化する
8. 製品や組織に合わせて複数の方法を組み合わせる

重要なのは「どの方法論が最も新しく優れているか」ではなく、何が事前に決められ、何が実際に作ってみないと分からないかを見極めることです。

仕様が固定された安全回路と、利用者の反応を見ながら改善する画面では、適した進め方が異なります。同じ製品の中でも、部分ごとに方法を使い分けるのが現実的です。
